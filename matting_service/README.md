# matting_service

An HTTP server for a background-removal (matting) model, so MindRouter can
answer `background: "transparent"` on `/v1/images/generations` and
`/v1/images/edits`.

The image model cannot do this itself. FLUX.2 Klein's decoder has three colour
channels and no alpha, and asking for transparency in the prompt only changes
what is drawn: Klein paints a grey-and-white checkerboard. So the gateway
generates (and watermarks) the picture as usual, then asks this server which
pixels are the subject.

## What it does

- `POST /v1/matte`: the request body is the image bytes (PNG, JPEG or WebP).
  The reply is `image/png`, an 8-bit greyscale **matte** of the same size:
  255 = subject, 0 = background. Headers: `X-Matting-Model`,
  `X-Matting-Seconds` (model time) and `X-Matting-Coverage` (mean matte value,
  0 to 1).
- The reply is only the matte, never a recoloured picture. The gateway attaches
  it to its own watermarked pixels (`backend/app/services/image_matting.py`),
  so this server decides which parts of a picture show and nothing else.
- A bearer key (`MATTING_API_KEY`). Without one the service refuses to start
  unless `MATTING_ALLOW_NO_AUTH=1`.
- One inference thread with a bounded queue in front: beyond
  `MATTING_MAX_QUEUE` waiting pictures the answer is `503` with `Retry-After`.
- A caller that disconnects while waiting is dropped from the queue.
- `GET /health`: `{"status": "ok"}` for anyone (`"loading"` while the weights
  load); model, device, queue depth and counts with the key.
- The picture's type is read from its own first bytes, its size from its
  header before any pixel is decoded (`MATTING_MAX_PIXELS`), and its length
  while reading (`MATTING_MAX_BODY_BYTES`, 413 above it).
- Nothing about a picture is logged or written to disk. Failures log their
  type only.

## Settings (environment)

| Variable | Default | Meaning |
|---|---|---|
| `MATTING_API_KEY` | (required) | Bearer key callers must send |
| `MATTING_MODEL` | `ZhengPeng7/BiRefNet_dynamic` | HF repo id or a local snapshot directory |
| `MATTING_REVISION` | (none) | Commit of the model repo to load. **Set it**: the repo's code is executed at load |
| `MATTING_SERVED_NAME` | `birefnet-dynamic` | Name reported in `X-Matting-Model` and `/health` |
| `MATTING_DEVICE` | `cuda` | Torch device (pick the card with `CUDA_VISIBLE_DEVICES`) |
| `MATTING_HALF` | `1` | Half precision on a GPU (`0` = full precision). Ignored on `cpu` |
| `MATTING_SIDE` | `1024` | The model's square input size |
| `MATTING_HOST` / `MATTING_PORT` | `127.0.0.1` / `18006` | Bind address; put nginx TLS in front |
| `MATTING_MAX_QUEUE` | `16` | Waiting pictures before 503 |
| `MATTING_MAX_BODY_BYTES` | `12582912` | Request body limit, 12 MiB (413 above it) |
| `MATTING_MAX_PIXELS` | `4194304` | Largest picture, 2048 x 2048 (422 above it) |

## The model

[BiRefNet](https://github.com/ZhengPeng7/BiRefNet) (MIT), the `BiRefNet_dynamic`
checkpoint: 220 M parameters, 444 MB of weights. It is loaded the way its model
card documents, through `transformers` with the repository's own code
(`trust_remote_code`). That code runs in this process, so:

- download the snapshot once, read `birefnet.py` and `BiRefNet_config.py`,
- set `MATTING_REVISION` to the commit that was read (or point `MATTING_MODEL`
  at the local snapshot directory), and
- run with `HF_HUB_OFFLINE=1` (the unit template does) so a restart can never
  pull newer code.

### Why this checkpoint (comparison of 2026-10-06)

24 pictures generated by production FLUX.2 Klein at 1024 x 1024, each cut
out and judged by eye on a magenta background. The first 12 (photos, a flat
icon, an emblem, glass, hair, smoke, a white mug on white, and two prompts
that asked for a "transparent background") went through five MIT-licensed
BiRefNet checkpoints; the second 12 (icons, badges, a sticker, line art, a
wordmark, a trophy) through the best two.

| Checkpoint | Pictures | Result |
|---|---|---|
| `BiRefNet_dynamic` | 24 | Clean on all 24, including both pictures where Klein drew a checkerboard. Thin smoke and a neon glow are dropped; a drop shadow is removed |
| `BiRefNet` (general) | 24 | Clean on 23; removed a third of a round emblem that touched the frame |
| `BiRefNet_lite` (44 M) | 12 | Removed the blue field of that emblem, keeping only its ring |
| `BiRefNet_HR-matting` | 12 | Soft mattes: the emblem, a logo and a balloon came out partly see-through |
| `BiRefNet-matting` | 12 | Kept the smoke, but lost the bottom of the emblem and half of a logo |

`briaai/RMBG-2.0` was not tried: its licence is non-commercial and the
repository is gated. `trmz/flux2-klein-alpha` (an alpha decoder plus
extraction LoRAs for Klein *Base*) was a week old and needs a different base
model than the distilled Klein the cluster runs.

Speed and GPU memory have not been measured on a GPU node yet (the comparison
ran on a laptop at about 10 s per picture). Fill this in at deployment.

## Install and run

```bash
python3 -m venv /path/to/.venv-matting && . /path/to/.venv-matting/bin/activate
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu128
pip install -r matting_service/requirements.txt

export HF_HOME=/path/to/hf-cache
hf download ZhengPeng7/BiRefNet_dynamic        # once; note the commit it prints

MATTING_API_KEY=... MATTING_REVISION=<commit> HF_HUB_OFFLINE=1 \
CUDA_VISIBLE_DEVICES=1 python -m matting_service

curl -s -H "Authorization: Bearer $MATTING_API_KEY" --data-binary @picture.png \
     http://127.0.0.1:18006/v1/matte -o matte.png
```

`deploy/matting-service.service` is a systemd unit template. Put nginx TLS in
front of the port, as for the other node services.

## Connecting it to MindRouter

1. **Admin -> Images**, card *Transparent Backgrounds*: the server's URL, its
   key, and the switch. Until the switch is on, `background: "transparent"`
   returns the opaque picture with `has_alpha: false`.
2. **Admin -> Backends**: register the SAME URL with engine *Matting server*.
   It is then health-polled like every other backend, and the images path
   skips it (returning opaque pictures) while it is unhealthy, disabled,
   draining or its circuit is open. Without this registration the server is
   simply dialed on every request.

## Tests
